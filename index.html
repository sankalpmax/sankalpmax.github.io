CI/CD case study: from commit to a checked deployment

The problem: building four services by hand and updating containers on EC2 is slow and easy to get wrong, and it leaves no record of which version is running. The workflow replaces that with one repeatable path. It builds each component, tags it with the commit, scans and publishes it, then deploys and checks it.

Limits and next improvements

  • The workflow has no unit, integration, or frontend test jobs and no lint step
  • Trivy findings do not block publishing, so the next step is a severity threshold that fails the build
  • There is no approval gate or dev-to-prod promotion in this workflow
  • AWS access uses stored keys, and moving to OIDC role assumption would remove them

Design notes

Application delivery path

A change pushed to GitHub starts a GitHub Actions workflow that builds the service images and runs a Trivy scan. The scan reports findings but does not fail the build, so it is informational only. Images go to Amazon ECR, then AWS Systems Manager deploys them to the AWS sandbox, and a health check follows. A later run completed with the health checks passing.

Infrastructure path and why two repositories

Terraform lives in its own repository so infrastructure changes are reviewed and applied separately from application releases. The Mumbai root keeps state in S3 with a native lockfile. The Hyderabad root uses local state by default, which is fine for learning but not for a team. There are no reusable modules yet.

Runtime and what the audit found

The read-only audit compared AWS inventory, Terraform source and state. Where it looked, it saw one running EC2 instance and a stopped RDS instance. It did not confirm the load balancer, the origin behind CloudFront, extra web servers, or a read replica, so those appear as “to verify” or “target design” rather than as built.

My next steps
  • Document the root cause of the earlier health-check failures
  • Add automated tests to the workflow
  • Make the Trivy scan block on high-severity findings
  • Add an approval step before deployment
  • Move Hyderabad to remote state and split the Terraform into modules
